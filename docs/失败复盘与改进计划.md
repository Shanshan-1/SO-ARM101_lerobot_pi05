# π₀.₅ 真机抓取失败复盘与改进计划

## 1. 证据边界

- **已核实**：公开数据集包含 40 条示教、17,961 帧、两路相机；公开模型的训练配置记录 5,000 steps、batch size 8、`train_expert_only=true`、`freeze_vision_encoder=true`、`eval_split=0.0`、`eval_steps=0`。见[数据集元信息](https://huggingface.co/datasets/Shanshan777/lerobot_dataset_01_20261014_233057/blob/main/meta/info.json)和[模型训练配置](https://huggingface.co/Shanshan777/lerobot_pi05_01/blob/main/train_config.json)。
- **视频可见**：约 17 秒片段和新增的约 60 秒记录均显示机械臂向目标区域运动，但没有展示稳定夹取并抬升。两段录像只能说明可见的执行现象，不能给出成功率或根因。
- **项目反馈**：真机任务成功率几乎为 0，尚无公开的逐次评估表，不应写成精确成功率。
- **训练日志**：[W&B 项目页](https://forge.coreweave.com/wandb/1808025338-tinghua/pi05/overview)可能需要登录或权限；此文不引用无法核对的 loss 数值、训练时长或吞吐。

## 2. 排查假设与验证实验

| 优先级 | 假设与依据 | 最小验证实验 | 如何判定 |
| --- | --- | --- | --- |
| P0 | **相机／预处理不一致**：基础模型声明三路相机槽位，微调模型是 `front`、`wrist` 两路；操作手册还指出远程推理可能把 4:3 图像直接拉伸到 224 × 224。 | 保存训练数据样本与推理时送入模型的两路图像，对照相机语义、顺序、尺寸、补边和颜色；确认是否使用远程推理客户端及其预处理。 | 两端同一场景的模型输入应有一致的几何变换和相机含义；修正前后在相同测试集比较。 |
| P0 | **动作和标定链偏差**：视频中接近目标却未抓起，可能涉及夹爪方向、动作尺度、初始姿态或坐标定义。 | 检查 checkpoint 随附的 pre/postprocessor 与归一化统计量；在安全条件下逐关节验证动作方向、夹爪开合，再回放一条示教动作。 | 若示教动作本身无法稳定完成同任务，先修控制或标定，不重训模型。 |
| P1 | **示教质量与覆盖不足**：40 条同一任务、约 10 分钟示教；接触前的速度、夹爪闭合时机、物体位置与恢复动作是否充分，尚未逐条审核。 | 给 40 条示教按“接近／对位／闭合／抬升”分段并打质量标签；比较失败初始状态与示教分布，再补采干净且场景多样的示教。 | 同等采集时长下比较原始数据与精选／多样化数据的真机阶段成功率；不能只看训练 loss。 |
| P1 | **失败状态缺少纠正示教**：若数据几乎全是理想轨迹，策略一旦偏离就可能无法恢复；目前是否缺失需要查看示教。 | 在有人监护下运行策略，记录临近失败时的人为纠正片段，单独构建增量数据集。 | 固定训练与评估方案，比较加入纠正片段前后的夹住、抬起比例，并同时检查原有场景是否退化。 |
| P1 | **微调范围受限**：`train_expert_only=true` 且 `freeze_vision_encoder=true`，视觉语言主干未针对现场更新。 | 先排除输入与执行链问题；之后在同一数据上比较可负担的微调范围。若需要全量微调，先确认显存与预算。 | 以同协议的真机结果判断。Dream Machines 的全量微调与 LoRA 对比不等同于本项目的 expert-only 设置。 |
| P1 | **推理重规划不足**：配置为 `n_action_steps=50`，30 fps 下对应约 1.67 秒；若整段动作执行后才观察，夹爪接触前可能来不及纠偏。 | 固定 checkpoint、相机与场景，测量实际推理延迟，比较完整 50 步执行与较短执行／更频繁观察；仅在当前实现支持时测试动作融合。 | 分阶段统计接近、夹住、抬升，另外记录抖动、延迟和安全停止次数。 |
| P2 | **训练进度与泛化不明**：实际配置 5,000 steps，`eval_split=0`、`eval_steps=0`；缺少留出集和 checkpoint 真机对照。 | 按 episode 留出验证集，保存若干 checkpoint，在同一批起始条件下评估。 | 不把验证损失最低当作最终选择标准，按真机阶段成功率与稳定性选型。 |

**注意**：`rename_map={}` 与两路相机配置是已核实的事实，但模型也可能按该配置正确训练和推理；仅凭配置差异不能判定具体故障。预处理问题同样需要先确认本次是否使用了手册描述的远程推理路径。

## 3. 外部经验如何用于本项目

参考：[Dream Machines, *Empirical results fine-tuning π₀.₅ on a real manufacturing task*](https://dream-machines.eu/blog/pi05-fine-tuning)（2026 年 9 月）。博客研究的是不同的双臂工业任务，约 21 小时主数据、50 Hz 控制和多轮真机评估；本项目是 SO-101 单臂抓取、约 10 分钟示教、30 fps。以下是**实验设计依据，不是本项目失败的证据**。

| 博客中的观察 | 对本项目的启发 | 不可直接照搬之处 |
| --- | --- | --- |
| 固定采集时长下，跨场景数据优于单一场景；额外高质量示教也改善了其任务成功率。 | 先审核 40 条示教的抓取质量，再用相同采集预算比较“重复原场景”与“物体位置、起点、光照变化”的数据。 | 不引用博客的百分点作为 SO-101 预期收益。 |
| 针对策略错误的人为干预数据带来明显改善。 | 从本项目常见的对位偏差、过早闭合、滑脱等失败点采集纠正片段；保留普通成功轨迹，避免只学到纠正动作。 | 先确认操作安全和数据格式；干预数据不能替代基础示教质量。 |
| 相同 checkpoint 在不同实时动作块重规划／融合设置下表现不同。 | 无需先重训：测量实际推理时延，在现有代码支持范围内比较短执行段和更频繁观察。 | 博客的 50 Hz、RTC 参数与本项目 30 fps 和实际部署路径不同；不能直接复制其 `reinfer`／`blend` 数值。 |
| 验证 action error 或 loss 不能可靠区分较好的 checkpoint；40 次 rollout 仍有较宽的不确定区间。 | 保留验证集诊断过拟合，但用预先定义的真机任务指标选 checkpoint；报告成功次数与总次数。 | 小样本下几个百分点的差异可能是波动；不足以宣布改进有效。 |
| 其新机器人任务中，全量微调优于测试的 LoRA 方案。 | 若数据与执行链已对齐而仍失败，再考虑扩大微调范围。 | 本项目是 expert-only，并非博客的 LoRA；RTX 4090 24 GB 也不能据其配置直接做全量微调。 |

## 4. 下一轮实验顺序

1. **冻结当前版本**：保存模型 commit、数据集版本、LeRobot 版本、相机编号、标定文件和推理命令；录制两路相机原图及送入模型的处理后图像。
2. **先做无模型基线**：回放示教轨迹，确认机械臂、夹爪与任务场景本身能完成抓取；若失败，优先修复硬件／标定／动作映射。
3. **建立评估表**：先定义“夹住并抬起目标”为主成功判据；固定物体与机械臂起始条件，每组尽量做 30–40 次，记录“接近／对位／夹住／抬起”和失败视频；再加入不同物体位置的变化场景。报告成功次数／总次数，而不是只写单个百分比。
4. **先做无需重训的对照**：在相同 checkpoint 上依次测试相机预处理、动作／夹爪映射和推理重规划；每次只改一个主要变量，记录时延与安全停止。
5. **补数据与验证集**：先审核并清理现有轨迹，再补采多位置、高质量示教；从实际失败中获取纠正片段；按 episode 切分训练／验证，避免相邻帧泄漏。
6. **最后比较训练方案**：保持测试场景与次数一致，比较不同 checkpoint、数据版本和可运行的微调范围。验证指标用于诊断，最终以真机分阶段结果决策。

建议每次试验至少记录：`模型版本｜数据版本｜相机与标定版本｜起点/物体位置｜执行步数/重规划设置｜推理延迟｜是否接近｜是否夹住｜是否抬起｜失败类型｜视频文件`。这样才能区分感知、动作、数据和时序问题。
